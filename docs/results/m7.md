# M7 native keyboard: experimental subset, not milestone completion

Baseline: main `3d9adbf`. Branch: `m7-native-keyboard`. Native is opt-in via
`NIRI_COMPUTER_USE_KEYBOARD=native`; wtype remains the default and is selectable
explicitly. Multi-monitor is deferred because the user has one monitor. The
single-output gate is unchanged.

## Implemented and tested

- The compositor's XKB keymap, active layout, direct Unicode symbols and keysyms
  resolved by libxkbcommon. Since round 2, text symbols the layout lacks go on spare
  keys of a call-long extended copy, and the compositor's map must come back byte
  for byte (below). No automatic fallback to wtype.
- Individual key pairs with focus/layout and stop checks between them. Native
  Ctrl+a / Hello repeated 20 times each; exact press/release pairs and zero final
  modifiers. Native focus mismatch and Ctrl+Shift+F12 application-only routing
  reuse the M4 checks. Observer keymap format/size remain unchanged during the
  native takeover trial (not a physical-restoration or content-hash test).
- `keys` (up to five modifiers) held during click, drag and scroll, only with the
  native backend selected. One marker covers both devices. wev observes mask 5
  (Control+Shift) at each tested pointer event and zero at the end.
- Stop/cancel during native typing and held drags: no later submission, balanced
  key/button state, zero modifiers and acknowledged cleanup before marker removal.
- SIGKILL during typing and a confirmed modifier-held pointer press: server B
  refuses `recovery_required`; recover sends native releases and pointer release,
  then B can acquire. Typing recovery releases the original wev keycode 38, not
  a fresh wtype synthetic mapping. Nested fixtures answer the human prompt; no
  actual application-state or physical recovery confirmation is claimed.
- Unchanged M4 wtype input criteria still run, including its UTF-8 text, routing,
  stop, crash/recover, kitty scrolling and 100/100 GTK button activations at both
  scales. Automatic C5, C9 virtual half and C10 corpus also pass with wtype.

The harness polls every 50 ms. Stop-command acknowledgement means the human CLI
finished writing the stop flag, not that the server watcher acknowledged it;
counts use subsequent complete wev log records and can be affected by logging
latency. Native reads the flag before each pair and also participates in the
existing watcher cancellation. Counts from the earlier pre-signal observation
were 2/1 characters after native stop at scales 1/1.5, and 1/1 after cancellation.
No Return landed in either takeover or native interruption trial.

wtype's takeover source logged 10 presses and 9 releases at both scales: focus
split one pair. This is additional baseline risk evidence, not proof of the
application's held state after focus re-entry. Native pairs remained balanced.

415.688 / 416.810 / 417.759 ms; scale 1.5
416.039 / 416.420 / 417.181 ms. The unchanged three-second gate passes.

## Blocking or unverified work

This is **not** M7 acceptance or default-promotion evidence:

1. Native types text beyond the layout only up to the map's spare keycodes at or
   below 255 (14 on the nested US map) in distinct missing symbols per call; more
   refuse whole, as do missing control characters and `key` keysyms. Dead-key or
   compose input is not used. Layout-specific ä/€ and group switching are covered
   with a controlled unit fixture, not live hardware layouts. Restoration is
   proved headless against an unfocused client, not against physical keys.
2. SIGKILL cannot run Drop, and niri does not release destroyed virtual devices.
   Since round 3 the crash guardian sends the marker's releases and the
   compositor's map without a human (below); the marker still waits for `recover`.
   It is proved headless, against wev and an unfocused client, not against physical
   keys or real applications' held state.
3. `paste` (round 3) is tested in one GTK 4 entry with a data-control owner of three
   types, not in terminals, Qt, browsers or Xwayland apps, nor with an image or a
   large selection. A read can't be traced to the app that made it.
4. An unfocused wl_keyboard subscriber cannot determine current physical modifier
   state. Native must remain experimental and isolated; preservation of active
   physical modifiers/locks is unverified.
5. C6 physical restoration, C7/C8 physical controls, C9 physical positive control,
   real application held/repeat state and lock transitions need the user present.
   Other modifier combinations, dynamic keymap changes, EOF/runtime-shutdown
   cleanup and fault/soak matrices are not fully proved. Application-level native
   text is shown for one GTK 4 entry only, not Qt, browsers, Xwayland or terminals.
6. Round 2's two native stalls (1618 ms and 853 ms) are explained in round 3: a
   timer tick per key on our side, fixed, and the nested winit backend's frame
   pacing outside it, which still stretches a call now and then, every round trip
   far inside the 2 s deadline (below).

No claim that every crash path immediately leaves no key held is made. The
marker and human recovery gate remain in force; native is not the default.

## Round 3: stalls, crash release and paste

Branch `m7-finish` off main `6c14f8e`. Commits: `01c0454` (harness pacer), `84350ee`
(zero-length waits without a timer tick), `366281d` (crash guardian), `879bcda`
(`paste`). Designs: `docs/decisions.md`, 2026-10-10 crash guardian and
clipboard-preserving paste.

### Native stalls

Measured with temporary, uncommitted per-phase timing in the server and a loop of the
native C10 and GTK entry cases, headless at scales 1 and 1.5:

- Before the fix, 3 loop runs (600 GTK entry calls, 180 wev calls) had 9 calls over
  300 ms, the longest 1296.9 ms, all in the GTK entry, which redraws on every key.
  No single round trip took over 30.99 ms: the stall was spread over every key.
- Our cause: the focus check after each key, `Waiter::until(Duration::ZERO)`, waited
  for tokio's next 1 ms timer tick, about 105 of the 117 ms a 100-key call took; the
  keys themselves took about 5 ms. Fixed in `84350ee`, with a regression test.
- The cause outside: in the nested winit backend, a round trip that arrives while
  niri renders waits for the frame, about 15 ms, sometimes two. Keys spaced by the
  timer tick fell into step with the frames: 100 × about 15 ms is the 1.6 s stall.
- After the fix, 3 loop runs, 780 native calls: the longest took 12.9 ms in the
  server, none stalled. A later 2-run loop, 840 calls with no build or other nested
  run active, had 6 slow calls (the longest 1668.6 ms); every slow round trip was a
  whole frame or two, at most 32.1 ms, about 60 times under the 2 s deadline, which
  is unchanged. The earlier loops didn't record whether a build was running.
- Native C10 tool to wev decoding all 100 characters fell from about 154 ms to about
  53 ms (min/median/max 53.152 / 53.969 / 54.871 at scale 1, 52.954 / 52.979 /
  53.010 at scale 1.5), and the GTK entry's native calls to the supervisor's 50 ms
  poll quantum. Native is now too fast for the mid-call checks to catch it typing,
  so a redrawing pacer window keeps a frame being drawn during them (`01c0454`).

### Crash release without `recover`

Killed with SIGKILL, the server's guardian released what the marker named; niri
acknowledged the releases this long after the kill (marker time, ms resolution),
and wev or the keymap observer saw them within the second figure (50 ms polling):

| Case | Scale 1 | Scale 1.5 |
|---|---|---|
| M4 drag button, no pacer | 1 ms; 101 ms | 1 ms; 102 ms |
| held drag button with Ctrl+Shift | 140 ms; 151 ms | 123 ms; 151 ms |
| native typing `A` | 63 ms; 102 ms | 63 ms; 101 ms |
| native typing `é`, extended map | 62 ms; 101 ms | 79 ms; 109 ms |

The pacer's frame pacing is in the native and held-drag figures. In the `é` case the
observer saw the compositor's map byte for byte before `recover` ran. The marker
stayed each time until `recover`. With the guardian replaced by `/bin/true`, the
suite failed at `m7-guardian`.

### Paste

Headless, in the GTK entry, through the main wtype server and then a native one:

- With nothing copied yet in the session, a paste reported `{"read": true,
  "clipboard": "cleared"}` and the clipboard stayed empty for a second.
