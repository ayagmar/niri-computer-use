# M9 results

Accessibility elements and element-aimed pointer tools, on branch `m9-elements` from `main` at `6b8f4b3`.

Environment: Rust 1.99.0; niri 26.04 (8ed0da4); cage 0.3.1; grim 1.5.0; Noctalia 5.2.1; at-spi2-core 2.60.7; GTK 4.22.5 and GTK 3.24.52 with PyGObject 3.56.3; Qt 6.11.2 (`qml6`, qt6-declarative). New Cargo dependency: `zbus` 5.19.0 (see `docs/decisions.md`).

Every nested run below ran in the private headless cage, with its own session bus and accessibility bus under `TEST_DIR`. No run read the host's accessibility bus, sent input to the host, or viewed host pixels, clipboard or window titles. Every run reported C1's host snapshot unchanged, no entries from its processes in the host's journal, and no leftover processes.

Each `nested-a11y` run also passed these checks:

- The accessibility bus's socket resolved under `TEST_DIR/run`, and the registry listed only processes of the nested session, before the fixtures, with each one, and after the server's checks.
- The server reported `accessibility.available: true` and listed `elements`.
- After niri moved the GTK 4 window by (+37, +11), the `Primary` element listed before the move still activated the button.
- A removed widget's ref came back `element_stale`. GTK answered the element's next call with `UnknownMethod: Object does not exist`.
- With Qt stopped by `SIGSTOP`, `elements` on the GTK 4 window answered in 105–106 ms, and on Qt's window failed with `deadline_exceeded` after 1.04–1.05 s: the first call to Qt hit its one-second deadline.
- `close_window`, then a click on the closed window's element: `element_stale` in 23, 41, 39 and 43 ms by the audit log.

The other suites start the server without an accessibility bus, so `elements` isn't listed there. The protocol tests check the same thing: `status.accessibility` says why, and a call to `elements` is a protocol error.

Artifacts are in `target/e2e/<run>/` and are not committed. Each `nested-a11y` run's audit log, up to the `close_window` check, is `audit.jsonl` there.

Durations are the server's own, from its audit log. They cover the calls logged before the `close_window` check: GTK 4's 101 clicks and, with SSD, Qt's 100. A hundred counted GTK 4 clicks took 5.4–5.5 s from the harness, including a counter read after each. Qt took 6.1–6.3 s and GTK 3 7.4–9.4 s. The slowest `elements` call each run is the first, which connects to the bus. These are samples from four runs, not latency guarantees.

The walk read 19 objects in GTK 4's window with client-side decorations and 9 with server-side ones, 4 in Qt's and 4 in GTK 3's.

## Not covered here

- Real applications on the user's accessibility bus: Firefox, Chromium and Electron apps, libadwaita apps, and Qt apps that don't set `QT_LINUX_ACCESSIBILITY_ALWAYS_ON`.
- Several outputs, rotated outputs, and windows partly off screen.
- A layer-shell surface, such as a Noctalia panel, covering an element: the server checks the element, not what is drawn on top of it.
